# MateClaw Browser Agent — Phase 3.1 Plan: Direct WSS + One-Click Pairing

Date: 2026-05-29
Author: Claude Opus 4.7 (1M context)
Status: **DRAFT — awaiting user sign-off before Wave 0**
Branch (proposed): `feat/browser-phase-3.1-direct-wss`
Motivation: user feedback — *"必须要这样做吗 这样用户使用起来很麻烦 能不能做到安装一个扩展就可以了"*

---

## 1. Why

Today MateClaw's only path from extension → backend is the **Native Messaging (NH) bridge**: a Go/Node binary the user must install, register in the OS (registry / `NativeMessagingHosts` dir), and restart Chrome for. That's a 4-step install. The official **Claude in Chrome** extension (analyzed from the store build, v1.0.74) proves a far simpler model:

- The extension's service worker opens a **direct WSS** to the backend (`wss://bridge.claudeusercontent.com/chrome/{token}`).
- The auth token is **pushed into the extension by the already-logged-in web app** via `chrome.runtime.sendMessage` (the manifest whitelists `claude.ai` under `externally_connectable`).
- NH is kept **only** as an optional path for local Claude Desktop / Claude Code to drive the browser.

We mirror that. The NH bridge stays in the tree as an **optional Claude-Code-integration path**, but stops being the default.

## 2. End-state user experience

```
1. Install the extension (load unpacked / store).
2. Open MateClaw admin UI (already logged in as admin).
3. Settings → Browser → see "🟢 Extension detected" → click [Connect Browser].
   (admin UI mints a PAT server-side and pushes it + the server URL into the
    extension over chrome.runtime.sendMessage — token never touches the clipboard)
4. Status flips to 🟢 Connected. Done.
```

Fallback when the admin UI origin is **not** in the extension's `externally_connectable`
whitelist (unknown / multi-tenant domains): the sidepanel has a manual
**Server URL + PAT** form. Still no NH bridge, still no OS-level install.

## 3. Layered design decision (locked)

**档 A (manual PAT entry) is the always-available foundation; 档 B (one-click push) is a convenience layer on top.**

Rationale: one-click depends on `externally_connectable`, which requires the admin
UI's origin to be hard-baked into the manifest. If the deployment domain isn't
whitelisted, one-click silently can't fire — so it must never be the *only* path.
The manual form underneath guarantees the feature works on any deployment.

## 4. Architecture: what changes vs. what's already correct

| Concern | Today | Phase 3.1 |
|---|---|---|
| extension → backend transport | NH bridge → backend WSS | **extension SW → backend WSS (direct)** |
| handshake auth | NH injects `Authorization: Bearer <PAT>` header | **`Sec-WebSocket-Protocol: mateclaw.edge.v1, bearer.<PAT>`** (browsers can't set Authorization) |
| WS origin policy | `setAllowedOrigins("")` (browser origins blocked) | `setAllowedOriginPatterns("chrome-extension://*", <admin origins>)` |
| session_id ownership | server issues on `HELLO_ACK`; NH stamps outbound | server issues on `HELLO_ACK`; **DirectBridgeClient stamps outbound** (same contract, NH role moves into the SW) |
| PAT delivery | user pastes into NH config | **admin UI one-click push** (档 B) / sidepanel paste (档 A) |
| device identity | none | **UUID `device_id`** persisted in `chrome.storage.local` (mirrors official) |
| liveness | edge `heartbeat` every 10 s (server-driven) | unchanged + client `ping` every 20 s (mirrors official, optional) |
| CDP execution | in-extension `chrome.debugger` ✅ | **unchanged** |
| content scripts (a11y, indicator) | ✅ matches official | **unchanged** |
| NH bridge | required | **optional** (Claude-Code path; default off) |

**Already-correct, do-not-touch:** the entire edge protocol envelope, `EdgeWebSocketHandler`
state machine, `BrowserSessionRegistry`, three-way session binding check (Codex P1-4),
the Phase 2 action/grounding/snapshot/screenshot stacks. Direct mode is purely a new
*transport + auth + bootstrap* shell around the existing protocol.

## 5. Wave breakdown

### Wave 0 — Backend handshake (the two blockers). ~45 min. **Serial, do first.**

- **W0.1 `EdgeAuthInterceptor.beforeHandshake`** — accept the bearer token from
  *either* `Authorization: Bearer <t>` (NH path, unchanged) *or* the
  `Sec-WebSocket-Protocol` header. Parse the comma-separated offered protocols;
  find the one shaped `bearer.<token>`; validate via the existing JWT-then-PAT
  cascade. Keep returning 401 on miss.
- **W0.2 subprotocol echo** — the browser closes the socket unless the server
  echoes an accepted subprotocol. Configure Spring to negotiate
  `mateclaw.edge.v1` (custom `DefaultHandshakeHandler.determineUser` won't do it —
  use `ServerEndpointConfig`/`setSupportedProtocols` on the handler registration,
  or a custom `HandshakeHandler` that sets `Sec-WebSocket-Protocol` to
  `mateclaw.edge.v1`). **Riskiest 30 min of the wave** — Spring's subprotocol
  negotiation has sharp edges; budget a focused spike.
- **W0.3 `WebSocketConfig`** — replace `.setAllowedOrigins("")` with
  `.setAllowedOriginPatterns("chrome-extension://*")` (plus admin-UI origins for
  belt-and-suspenders; auth is still the real gate).
- **Tests:** extend the edge handshake test — (a) token via subprotocol → 101 +
  echoed `mateclaw.edge.v1`; (b) token via Authorization still works (NH
  regression); (c) bad token via subprotocol → 401; (d) `chrome-extension://` origin
  accepted, random `https://evil.com` origin rejected.
- **Security note:** putting the PAT in `Sec-WebSocket-Protocol` keeps it out of the
  URL/query string, so it does **not** land in access logs (unlike the official
  `/chrome/{token}` path-style). This is deliberately better than the reference.

### Wave 1 — Extension DirectBridgeClient. ~3 h. Depends on W0.

- **W1.1 `src/sw/config-store.ts` (NEW)** — typed wrapper over
  `chrome.storage.local`: `{ serverUrl, pat, deviceId (UUID, lazy-created),
  deviceName }`. `getDeviceId()` mints+persists a `crypto.randomUUID()` on first
  read (mirrors official `bridgeDeviceId`).
- **W1.2 `src/sw/direct-bridge.ts` (NEW)** — WS client with the **same public
  interface as `NativeBridge`** (`connect/send/onMessage/onDisconnect/disconnect`)
  so `index.ts` is transport-agnostic:
  - `new WebSocket(serverUrl, ['mateclaw.edge.v1', \`bearer.${pat}\`])`
  - on open → send `HELLO` (session_id="", payload carries `agent_version`,
    `device_id`, `device_name`).
  - on `HELLO_ACK` → capture `session_id`; **stamp it on all subsequent outbound
    frames** (this is the NH's old job moving into the SW — update the P0-1 invariant
    comment in `edge-protocol.ts`).
  - `ping` every 20 s; reconnect with exponential backoff (cap ~30 s);
    surface state via `onStateChange(cb)`.
- **W1.3 `src/sw/index.ts`** — transport selection: if `config-store` has
  `{serverUrl, pat}` → construct `DirectBridgeClient`; else stay idle (no auto
  `connectNative`). NH becomes opt-in (W3 surfaces the toggle). All existing
  handler wiring (TabGroupManager, DebuggerManager, ActionExecutor, …) is unchanged —
  it binds to whichever transport's `send`/`onMessage` it's handed.
- **Tests:** `direct-bridge.test.ts` with a mock `WebSocket` — HELLO/HELLO_ACK
  session_id capture + stamping; reconnect/backoff; ping cadence; subprotocol array
  shape. Mirror the existing `native-bridge.test.ts` structure.

### Wave 2 — Bootstrap + sidepanel (manual path = 档 A). ~2 h. Depends on W1.

- **W2.1 `src/sw/index.ts` onMessageExternal** — listen for messages from
  whitelisted origins:
  - `{type:'ping'}` → `{alive:true, deviceName, connected}` (lets admin UI detect
    the extension — mirrors official `ping`).
  - `{type:'pair', pat, serverUrl, deviceName?}` → validate origin, persist to
    config-store, (re)connect DirectBridgeClient, ack `{ok:true}`.
  - `{type:'unpair'}` → clear config, disconnect.
- **W2.2 `manifest.json` + `public/manifest.json`** (keep the two in sync — known trap):
  - add `externally_connectable.matches` (localhost now; prod domain placeholder
    documented — see §6).
  - broaden CSP `connect-src` to the WSS target(s).
  - add a pinned `"key"` so the extension ID is **deterministic** across installs
    (required so the admin UI can target a known ID — mirrors official `key`). Generate
    a fresh RSA keypair; record the derived 32-char ID in §6 + the admin component.
  - keep `nativeMessaging` permission (optional path).
- **W2.3 `src/sidepanel/App.vue`** — add a Settings panel above the ping log:
  Server URL + PAT (password) inputs, [Save & Connect] / [Disconnect], a live
  connection-status pill driven by `DirectBridgeClient.onStateChange`. This is the
  档 A fallback and the primary debugging surface.

### Wave 3 — Admin UI one-click (档 B). ~3 h. Depends on W2. Parallelizable with W4 doc.

- **W3.1 backend PAT-mint endpoint** — confirm/extend `PersonalAccessTokenController`
  to mint a **browser-scoped** PAT for the logged-in admin (scope `browser:edge`,
  short-ish TTL, name `"browser-extension/<deviceName>"`). Likely a thin wrapper over
  existing create.
- **W3.2 admin UI "Browser Pairing" card** (Vue, under `mateclaw-ui` Settings):
  - on mount: `chrome.runtime.sendMessage(EXT_ID, {type:'ping'})` (guarded — `chrome`
    may be undefined; component degrades to "extension not detected / install it").
  - [Connect Browser] → `POST` mint PAT → `chrome.runtime.sendMessage(EXT_ID,
    {type:'pair', pat, serverUrl: deriveWs(location.origin), deviceName})` → poll
    ping for `connected:true` → flip status pill.
  - [Disconnect] → `{type:'unpair'}` + revoke the PAT.
  - `EXT_ID` baked from W2.2's deterministic ID.
- **Tests:** component test with a mocked `chrome.runtime` (detected / not-detected /
  pair-success / pair-rejected). Backend: PAT-mint endpoint test (scope + TTL +
  owner).

### Wave 4 — Integration, smoke, docs. ~1 h. Depends on W3 (or W2 for 档 A-only smoke).

- **W4.1** end-to-end smoke runbook: fresh Chrome profile → load unpacked → admin UI
  one-click → status green → run `extension_browser_navigate` + `_click` from a real
  agent turn → CDP events land. Update `docs/specs` + the install runbook; mark NH as
  optional.
- **W4.2** full sweep: `mvn test` (server), `pnpm test` (extension), `pnpm build`
  (extension + UI), Phase 1 audit script GREEN.

## 6. Open items needing a value before/while building

- **Deployment domain for `externally_connectable`** (user didn't pick): plan ships
  with `http://localhost:18088/*` baked in + a clearly-marked `// PROD_DOMAIN` slot.
  Add your domain + rebuild the extension to enable one-click there; otherwise 档 A
  (manual paste) covers it. **No code blocks on this** — localhost works out of the box.
- **Deterministic extension `key`/ID**: generated in W2.2, recorded here and in the
  admin component. (Unpacked installs otherwise get a path-derived ID that the admin
  UI couldn't target.)

## 7. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Spring subprotocol echo doesn't negotiate cleanly (W0.2) | Spike first; fallback to a custom `HandshakeHandler` that force-sets the response `Sec-WebSocket-Protocol`. Time-boxed to 30 min before escalating. |
| Allowing `chrome-extension://*` origin broadens attack surface | Token (PAT/JWT) is still the gate; subprotocol carries it; origin pattern only *admits the handshake*, doesn't authorize. Same trust model as the official extension. |
| Two manifests drift (`manifest.json` vs `public/manifest.json`) | W2.2 edits both in one change; add a note to the existing sync trap in CLAUDE.md if not already covered. |
| `chrome.runtime.sendMessage` undefined in non-extension browsing context | Admin component feature-detects and degrades to "install the extension" copy. |
| PAT in query string leaking to logs | Avoided by design — we use `Sec-WebSocket-Protocol`, not a path/query token. |
